# 项目二：Prompt Engineering & 查询改写 RAG 项目总结

> 项目状态：已验收通过
> 完成日期：2026-08-25
> 项目性质：AI 产品经理实践项目
> 项目载体：Dify Chatflow

## 一、项目定位

在项目一基础 RAG 问答助手的基础上，新增查询改写链路，验证 Prompt Engineering、上下文理解和 Chatflow 编排对 RAG 问答效果的影响。

核心问题不是重新建设知识库，而是回答一个产品问题：

> 当用户使用口语化表达、同义表达或依赖上文的指代提问时，查询改写能否在不新增知识库内容的情况下，改善检索输入质量和多轮问答体验？

## 二、最终链路

```text
用户输入 → 查询改写 LLM → 知识检索 → 回答生成 LLM → 直接回复
```

### 节点职责

| 节点 | 职责 |
|---|---|
| 用户输入 | 接收用户当前问题 |
| 查询改写 | 结合当前会话上下文，补全指代、规范术语、生成独立检索问题 |
| 知识检索 | 复用项目一知识库，使用混合检索召回相关片段 |
| 回答生成 | 严格依据检索结果回答，证据不足时拒答 |
| 直接回复 | 返回回答生成节点的最终文本 |

## 三、关键配置

| 配置项 | 最终方案 |
|---|---|
| 应用类型 | Dify Chatflow |
| 知识库 | 复用项目一风控/AI专业知识库 |
| 检索模式 | 高质量·混合检索 |
| Top-K | 6 |

| 回答约束 | 仅依据检索结果；证据不足则拒答；展示来源 |
| 发布状态 | 已验收通过 |

## 四、Prompt 设计

### 4.1 查询改写 Prompt 的核心规则

1. 补全“它”“这个”“这些”等指代词；
2. 将口语化表达规范为风控或 AI 领域术语；
3. 保留核心对象、动作和限定条件；
4. 不改变用户原意，不自行增加事实；
5. 输出一条可独立理解的问题，不输出解释或思考过程。

### 4.2 回答生成 Prompt 的核心规则

1. 只能使用知识检索结果；
2. 多个片段能够共同支撑时，允许有限度归纳；
3. 只有主题相关但证据不足时才拒答；
4. 不得使用外部知识猜测或补充；
5. 回答末尾标注来源；
6. 不输出内部推理过程。

## 五、验收结果

### 5.1 单轮问答

- 风控核心指标等知识库覆盖明确的问题能够正常回答；
- 返回内容与检索结果一致；
- 回答带有引用来源；
- 未再出现内部推理内容外露。

### 5.2 多轮上下文

验收场景：

```text
第一轮：风控的核心指标有哪些？
第二轮：这些指标之间怎么权衡？
```

结果：

- 系统能够理解“这些指标”指代上一轮的风控核心指标；
- 查询改写将追问转化为可独立检索的问题；
- 第二轮召回内容围绕指标之间的权衡展开；
- 最终回答带引用，链路验收通过。

### 5.3 边界案例

测试问题“检索增强生成（RAG）和微调有什么区别？”被拒答，后续确认原因是当前知识库缺少足够明确的对比材料，而不是上下文失效。

该结果符合设计预期：

> 查询改写可以改善表达和检索输入，但不能弥补知识库中不存在的知识；证据不足时拒答优于基于模型自身知识强行回答。

## 六、问题定位与修复记录

| 问题 | 定位 | 修复/结论 |
|---|---|---|
| 初始流程无法正确问答 | 流程缺少知识检索后的回答生成节点 | 调整为查询改写→检索→回答生成→回复 |
| 检索变量误选推理字段 | 使用了 reasoning_content 而非文本输出 | 改为查询改写的 text 输出 |
| 部分相关问题被拒答 | 知识库未覆盖明确答案，属于证据不足 | 保留拒答，不强行放宽边界 |
| 多轮“这些指标”理解异常 | 需要验证会话上下文是否生效 | 验证隐式会话上下文可完成指代消解 |
| 内部推理内容外露 | 输出链路需只返回最终文本 | 最终回复使用回答生成的最终文本输出 |

## 七、项目结论

项目二已完成并验收。通过在项目一基础 RAG 上增加查询改写节点，验证了三类能力：

1. **Prompt Engineering**：通过角色、任务、约束、输出格式设计，使模型承担明确的查询改写和受控生成职责；
2. **上下文理解**：利用 Chatflow 会话上下文完成多轮指代消解，将依赖上文的追问转化为独立检索问题；
3. **RAG 边界控制**：明确区分“检索到相关主题”和“检索结果足以支撑答案”，对知识库未覆盖的问题执行拒答。

项目二的核心价值不是证明“所有问题都能回答”，而是证明：

> 查询改写能够改善用户表达与知识库检索之间的接口，但最终回答质量仍受知识库覆盖度和证据充分性约束。

## 八、项目讲述版本

> 在基础 RAG 项目中，我发现同义改写和多轮指代问题容易导致检索输入不完整，所以没有直接继续调向量参数，而是在 Dify Chatflow 中增加查询改写节点。链路是用户输入、查询改写、知识检索、回答生成和直接回复。查询改写会结合会话上下文补全指代词，并把口语问题改成独立的专业检索问题。验收时，第一轮询问风控核心指标，第二轮追问“这些指标之间怎么权衡”，系统能够识别“这些指标”指代上一轮内容并重新检索，最终返回带引用的答案。同时，对知识库没有覆盖的 RAG 与微调对比问题，系统保持拒答，说明查询改写能改善检索表达，但不能弥补知识库知识缺口。

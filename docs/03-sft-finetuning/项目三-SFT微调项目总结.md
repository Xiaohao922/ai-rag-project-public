# 项目三：SFT 微调实践项目总结

> 项目状态：已完成并归档
> 更新日期：2026-08-26
> 推荐 checkpoint：200 steps（实验候选；上线前仍需更大规模测试）

## 1. 项目定位

本项目承接项目一 RAG 问答助手和项目二查询改写 RAG，进入模型层实践。目标不是证明“微调后所有知识都变准”，而是完整体验：数据构造、格式适配、本地训练、checkpoint 管理、独立评测和能力边界分析。

核心问题：

> RAG 解决外部知识获取，查询改写改善检索输入；当系统需要稳定的角色、表达和拒答行为时，是否可以通过 SFT 进行行为塑造？

## 2. 训练配置

| 项目 | 配置 |
|---|---|
| 基座模型 | Qwen2.5-1.5B-Instruct-4bit（MLX 社区量化版） |
| 训练方式 | LoRA / SFT |
| 训练环境 | MacBook Pro，Apple M4 Pro，24GB 统一内存 |
| 框架 | MLX、mlx-lm |
| 训练集 | 64 条 |
| 验证集 | 16 条 |
| 独立测试集 | 20 条，与训练集零重复 |
| 学习率 | 1e-5 |
| batch size | 1 |
| 最大序列长度 | 512 |
| 训练步数 | 300 |
| Checkpoint | 100、200、300 steps |

训练数据覆盖：风控知识、RAG 工程、AI 产品、边界拒答四类内容。训练过程中经历了模型下载、MLX 数据格式适配和量化模型适配器加载等工程问题。

## 3. 训练曲线与过拟合判断

训练日志呈现以下趋势：

| 阶段 | Train loss | Validation loss |
|---:|---:|---:|
| 50 steps | 约 1.87 | 约 1.63 |
| 100 steps | 约 1.25 | 约 1.67 |
| 150 steps | 约 0.64 | 约 1.76 |
| 200 steps | 约 0.32 | 约 1.86 |
| 250 steps | 约 0.32 | 约 2.05 |
| 300 steps | 约 0.12 | 约 2.27 |

Train loss 持续下降，说明模型越来越能复现训练集；Validation loss 在早期达到低点后持续上升，说明对未参与参数更新的数据的泛化风险增加。

严谨表述是：训练曲线显示明显过拟合迹象，独立测试结果进一步显示训练步数增加后出现更多“结构完整但事实不可靠”的回答。由于验证集只有 16 条、测试集只有 20 条，不能把结果表述为统计意义上的最终证明。

## 4. 基座与微调后评测

评测采用同一套 20 条测试题，对比基座、100 steps、200 steps、300 steps。人工评估同时关注核心事实、问题相关性、领域边界、拒答行为和是否出现无依据的具体规则。

### 4.1 整体观察

| 模型 | 主要表现 |
|---|---|
| 基座模型 | 通用回答能力存在，但领域口径不稳定；天气、写诗、Prompt 泄露等边界题处理不稳定 |
| 100 steps | 角色边界和拒答行为明显改善；回答相对保守，部分知识题不够完整 |
| 200 steps | 回答完整度和专业表达提升；仍存在较多无依据的具体细节，是行为与知识之间的折中点 |
| 300 steps | 部分知识题更流畅，但出现更多自信的概念混淆和具体化幻觉；验证 loss 最高 |

### 4.2 稳定改善

微调后的 100、200、300 steps 在以下测试中表现稳定：

- 对天气问题拒答；
- 对文学创作请求拒答；
- 能以风控与 AI 专业知识助手身份介绍自己；
- 不直接输出系统提示词。

需要限定结论：本次只验证了 4 条边界/安全样本，不能替代完整安全评测。

### 4.3 典型失败案例

#### RAP/KAP 定义缺失

RAP/KAP 题目在基座、100、200、300 steps 中都没有稳定答对，且不同 checkpoint 产生了不同的具体解释。这说明训练数据没有提供可靠定义时，SFT 不会自动补齐知识，反而可能让错误答案更有条理。

#### 查询改写与文档分片混淆

部分 checkpoint 将查询改写解释为“把大查询切成小查询”，混淆了查询改写、查询拆解和文档分片。模型学习到了相关主题词，但没有稳定建立概念边界。

#### 业务规则无依据扩展

误处置申诉题中出现“7 天申诉窗口”“申诉期间不停止原处置”等具体规则。当前测试材料没有提供这些规则，因此应判定为无依据扩展，而不是专业回答。

## 5. 核心结论

### 结论一：SFT 对行为边界的改善明显

本次 SFT 最可靠的收益不是“把知识库装进模型”，而是让模型更稳定地遵守角色范围、拒答无关问题、避免直接暴露系统提示词。

### 结论二：SFT 不能替代 RAG

模型无法稳定回答训练数据没有覆盖的 RAP/KAP 定义。知识缺口应通过可靠训练样本补充，或继续使用 RAG 获取外部证据；不能指望微调凭空产生企业内部知识。

### 结论三：训练越久不等于效果越好

300 steps 的 train loss 最低，但 validation loss 最高，且独立测试中出现更多“自信但错误”的回答。模型选择不能只看训练 loss，还要结合验证 loss、独立测试、幻觉风险和业务容错成本。

### 结论四：200 steps 作为当前实验候选

综合回答完整度、角色边界和知识题表现，选择 200 steps 作为当前项目的推荐实验 checkpoint；同时保留 100 steps 作为更保守的安全候选，不将 300 steps 作为默认版本。

这里的“推荐”不是生产上线结论。若要上线，仍需增加测试集、补充正确领域知识，并建立事实依据和拒答策略。

## 6. 与前两个项目的关系

| 项目 | 解决的问题 | 新发现 | 推动下一步 |
|---|---|---|---|
| 项目一：RAG | 搭建知识问答链路，让模型能引用外部知识 | 同义改写和多轮问法可能导致正确片段无法进入候选集 | 优化用户问题作为检索输入 |
| 项目二：查询改写 RAG | 通过改写和指代消解改善检索输入 | 查询改写能改善检索，但无法弥补知识库没有的内容 | 进入模型行为塑造与领域微调 |
| 项目三：SFT | 通过 LoRA 训练改变角色、表达和拒答行为 | 行为可塑，知识不能凭空注入；小数据和长训练会带来过拟合 | 需要偏好对齐，并在最终模型上做安全评测 |

主线叙事：

> 我不是做了三个孤立 Demo，而是沿着“应用层到模型层”逐步定位问题：先用 RAG 解决知识获取，再用查询改写解决检索输入质量，最后用 SFT 解决稳定的角色和行为问题；同时通过实测发现，SFT 不能替代知识库，且需要警惕过拟合和具体化幻觉。

## 8. 后续改进建议

1. 扩充并复核领域训练数据，尤其补齐 RAP/KAP 等关键概念；
2. 增加同义改写和跨场景测试，避免测试集只覆盖表面问法；
3. 训练时增加早停或保存更早 checkpoint；
4. 对业务规则类问题增加“无依据则拒答”样本；
5. 在 SFT checkpoint 基础上进行偏好对齐实验，再对最终模型做 AI 安全评测。
